# TASK 020 — FRONTIER-QUALITY LOOP + INDEPENDENT LOCAL BOOK BRAIN

**Status:** READY FOR CODEX IMPLEMENTATION  
**Milestone:** World-class nonfiction production quality / local-brain foundation  
**Owner:** BOOK OS Central Brain  
**Execution role:** Codex  
**Date:** 2026-09-09

## 0. Owner outcome

BOOK OS must produce nonfiction at the quality level demonstrated by the strongest current frontier-model work in high-compute/max-quality mode, while progressively reducing dependence on external model execution.

This task creates a two-lane architecture:

1. **Frontier lane now** — external best-available model execution through the existing provider-neutral BOOK OS gateway, with the current OpenAI lane available for the hardest work.
2. **Independent local BOOK OS Brain** — local/open-weight execution plus BOOK OS editorial intelligence, evaluated against the same human-owned quality contract and promoted operation-by-operation only when evidence shows it is strong enough.

The goal is quality parity by measured editorial outcome, **not imitation or reverse engineering of any proprietary model**.

## 1. Non-negotiable legal/data boundary

Do **not** use OpenAI output to train, fine-tune, distill, preference-train, synthesize a training corpus for, or otherwise develop a competing local model.

OpenAI output may be used for the user's normal book-production work and for bounded human evaluation of the external lane, but it must not become local-model training data.

Local model development/evaluation data must be rights-clean and independent, e.g.:

- Owner-authored/Owner-controlled manuscripts and editorial decisions where rights permit;
- purpose-built human-authored gold cases;
- licensed/open datasets compatible with the intended use;
- synthetic data generated by models whose terms permit that use;
- deterministic transforms and labels created by BOOK OS itself.

Tests/CI must use fixtures and make zero paid/provider calls.

## 2. Build-vs-reuse rule

Do not reinvent solved infrastructure. Prefer mature maintained components when they meet BOOK OS requirements.

### REUSE / ADOPT

#### OpenAI external intelligence lane

Use the current OpenAI platform capabilities where they materially reduce bespoke infrastructure:

- Responses API as the external execution surface;
- structured outputs / typed tool and response contracts;
- hosted web search and file search where appropriate for bounded external research workflows;
- function tools/MCP only through explicit BOOK OS adapters;
- Agents SDK patterns for bounded specialist orchestration when simpler direct orchestration is insufficient;
- OpenAI Evals/Graders as **supplemental** evaluation infrastructure where useful;
- response/conversation compaction for long tool-heavy external workflows where it does not create hidden authority;
- tracing/provenance hooks when they improve observability.

Do not make OpenAI Agents state, conversation state, vector stores or traces canonical BOOK OS authority. Canonical authority remains in BOOK OS local state.

#### Local inference on Apple Silicon

Primary local inference foundation: **Apple MLX / MLX-LM or an equivalent mature Apple-Silicon runtime with a stable local API**.

Requirements:

- runs locally on Apple Silicon;
- can be packaged so the end user does not manage Python/dev tooling;
- model weights/config are explicit and hashable;
- model license/usage rights are recorded;
- supports quantized models where useful;
- supports sufficiently long context for assigned operations;
- exposes deterministic capability metadata and health/readiness;
- can be replaced without changing BOOK OS authority semantics.

Do not hard-code one local model family as permanent authority.

#### Authoring/editor commodity layer

For future editor replacement work, prefer **Tiptap/ProseMirror** rather than building a rich-text engine from scratch. This task may define integration seams but must not derail into a full UI rewrite.

#### Research commodity sources

Reuse current OpenAlex/Crossref/Semantic Scholar and extend through adapters rather than duplicating their metadata infrastructure. Web/official-source research remains a separate evidence workflow.

### BUILD / KEEP AS BOOK OS IP

Do not replace these with vendor-owned black-box state:

- Authority Protocol;
- Book Contract / Architecture / Chapter Contract semantics;
- Series Canon / Exclusion Registry / Uniqueness Ledger;
- Chapter admission and `WRITING_ALLOWED` semantics;
- Book Graph and durable Book Memory semantics;
- Claim / Source / Evidence ontology and evidence gates;
- Author/Series/Style profiles and voice fingerprint semantics;
- Editorial Decision Memory;
- anti-junk / AI-prose pathology rules;
- BookBench dimensions, blocking logic and release criteria;
- independent editorial/adversarial review semantics;
- Literary Master and reproducible release semantics;
- quality-routing policy and promotion/demotion rules for local vs external executors.

## 4. Core quality loop

Implement a first-class orchestration object/service for nonfiction production. Do **not** represent this as a giant prompt.

For each admitted chapter, the normal high-quality path is:

`approved book authority`
→ `chapter admission`
→ `chapter micro-plan`
→ `evidence/research plan`
→ `section intent + contribution check`
→ `draft candidate`
→ `deterministic local checks`
→ `evidence/factual checks`
→ `semantic novelty / repetition check`
→ `independent critic/reviewer`
→ `targeted revision proposal`
→ `post-revision checks`
→ `human review/acceptance`
→ `next unit`

The exact number of model calls is not authority. BOOK OS may collapse steps when evidence shows quality is preserved, but it may not silently skip quality-critical checks merely to save cost or latency.

### Required quality properties

The loop must explicitly evaluate at least:

- chapter function fulfilled;
- new intellectual contribution exists;
- no padding/water;
- no semantic duplication with current book/series reservations;
- factual claims are traceable to evidence or explicitly marked as authorial/interpretive;
- argument is coherent and non-trivial;
- examples are specific and useful;
- reader progression is visible;
- style/voice constraints are met;
- transitions are functional rather than generic;
- prohibited AI-prose pathologies are surfaced;
- content does not silently exceed chapter/book boundaries;
- uncertainty/conflict in evidence is represented honestly.

## 5. Specialist architecture

Use a **manager + bounded specialists/tools** pattern. Avoid an unconstrained swarm.

Possible roles:

- Planner / Architect;
- Researcher;
- Evidence Analyst / Fact Checker;
- Writer;
- Developmental Critic;
- Line/Literary Editor;
- Adversarial Reviewer;
- BookBench Judge.

Rules:

- specialists return structured proposals/findings;
- no specialist can approve its own material output;
- canonical state transitions remain BOOK OS code-controlled;
- Writer and Critic should be independently routable where possible;
- the same model may fill multiple roles only when explicitly allowed by routing/eval policy and never converts model self-agreement into authority.

Agents SDK may be used inside the external lane if it simplifies orchestration/tracing, but BOOK OS Local Core remains the manager of canonical state and approvals.

## 6. Local Brain provider

Add a provider-neutral local executor lane, e.g. provider id `local`, without coupling BOOK OS to a specific model family.

Required concepts:

### Local model manifest

Persist/validate metadata such as:

- provider/runtime id;
- model id/version;
- source/license identifier;
- weights/config hash where available;
- quantization;
- context limit;
- supported task classes;
- tool/structured-output capabilities;
- memory/RAM requirement estimate;
- benchmark status by operation;
- promotion state: `EXPERIMENTAL | SHADOW | ELIGIBLE | PREFERRED | SUSPENDED`.

### Hardware capability probe

Provide a local capability/readiness report without downloading a model or making external calls in CI.

At minimum expose:

- Apple Silicon / architecture;
- available memory signal where safely obtainable;
- local runtime availability;
- configured local model availability;
- reason if a requested model cannot run.

### Local execution adapter

Use a narrow adapter compatible with existing ModelGateway semantics. Prefer a stable local HTTP or in-process interface; do not leak MLX-specific concepts into book authority.

The adapter must preserve:

- structured output validation;
- prompt/config version provenance;
- authority input hashes;
- latency/usage metadata where available;
- deterministic failure semantics;
- no network requirement for a configured local run.

## 7. Quality comparison and promotion system

Create an operation-level benchmark/promotion harness. A local model is never declared “as good as frontier” by anecdote.

### Benchmark units

Support bounded cases for at least:

- Book Contract proposal;
- architecture proposal;
- chapter contract/micro-plan;
- research synthesis with supplied evidence;
- section draft;
- developmental critique;
- targeted rewrite;
- contradiction/repetition diagnosis.

### Gold/evaluation data

Gold cases must be independent/rights-clean. OpenAI outputs must not be used as training targets for the local model.

A benchmark may compare two anonymous candidates for **human/editorial evaluation**, but benchmark output storage must be isolated from any local-model training corpus.

### Evaluation dimensions

Use BookBench plus explicit human rubric dimensions:

- correctness / evidence fidelity;
- intellectual depth;
- originality / non-banality;
- contract fulfillment;
- coherence / progression;
- specificity / usefulness;
- thought density;
- author voice/style fit;
- absence of machine-prose pathology;
- rewrite quality / preservation of meaning;
- unsupported-claim rate;
- unnecessary verbosity/padding;
- whole-book/series overlap risk where applicable.

### Promotion rule

Promotion is **per operation**, not global.

A local executor may become eligible/preferred for an operation only when:

- deterministic BLOCKING dimensions pass;
- human/eval sample is sufficiently sized for the current stage;
- no material quality regression is hidden by an average score;
- provenance is complete;
- Owner/Central Brain accepts the promotion rule/evidence.

If local quality is weaker for a hard operation, route that operation to the frontier lane. Do not lower the quality target to increase “local percentage”.

## 8. Frontier-quality benchmark profile

Create a named evaluation profile, e.g. `FRONTIER_QUALITY_V1`, representing the current highest-quality BOOK OS target.

It is **not** defined as “copy GPT-6 Astra wording”. It is defined by measurable editorial outcomes.

For external OpenAI benchmark executions, the harness must be capable of recording exact model id and reasoning/work level, including the highest supported bounded quality setting selected by the Owner for the benchmark run.

No paid benchmark is executed in this implementation task. Live benchmark runs require separate explicit Owner cost approval.

## 9. Editorial Decision Memory

Extend/reuse the existing editorial corpus so the system can learn operationally from Owner/editor decisions without immediately training a model.

Persist/retrieve, with private/local storage boundaries:

`input revision → finding/diagnosis → proposal → accept/reject/modify → reason → final revision`

Use first for:

- retrieval of similar prior decisions;
- prompt/context steering;
- style exception memory;
- BookBench calibration;
- routing/eval analysis.

Any later model training is a separate task with explicit data-rights review and Owner approval.

## 10. Research integration

Do not let “frontier quality” mean fluent unsupported prose.

The loop must be able to consume:

- current Claim/Evidence ledger;
- exact source pointers;
- current vs stale evidence;
- conflicting evidence;
- research-required flags from chapter/section planning.

For external research, hosted OpenAI web/file search may supplement existing adapters when explicitly selected, but retrieved material must be normalized into BOOK OS Source/Evidence objects before it can satisfy evidence gates.

## 11. Long-context strategy

Do not dump the entire book blindly into every request.

Implement/reuse context assembly based on:

- exact current authority;
- chapter contract;
- relevant Book Memory retrieval;
- series reservations/overlap candidates;
- relevant evidence;
- accepted style profile/examples;
- prior accepted manuscript units needed for continuity.

External response compaction/conversation state may optimize an execution lane, but it is derived cache only. If deleted, BOOK OS must be able to reconstruct the task from canonical local state.

## 12. Product behavior

Default UI must not expose agent plumbing, vector stores, trace ids or provider internals to ordinary author workflow.

User-facing behavior should eventually read like:

- `Write / Improve / Check evidence / Challenge argument / Reduce repetition / Compare versions`;
- one clearly visible current task;
- optional model/execution settings;
- clear findings and Accept / Reject / Edit decisions.

This task should add only the minimal UI needed to prove the quality loop and local/external execution readiness. The full world-class UX rewrite is a separate product task.

## 13. Observability / provenance

Every quality-loop run must make it possible to answer:

- what authority revisions were used;
- what research/evidence objects were used;
- which executor/model/runtime and work level were used;
- what prompt/config versions were used;
- which deterministic/semantic/judge checks ran;
- which findings caused revision;
- what changed between candidate/revised output;
- what the human accepted/rejected;
- whether any external/provider call occurred and its bounded cost metadata.

Do not expose hidden chain-of-thought. Store only supported provenance, structured reasoning summaries/findings and tool/run metadata.
